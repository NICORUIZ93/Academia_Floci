# Bloque 3: QA Automation

Este bloque contiene 6 roadmaps independientes. Cada roadmap avanza en 30 pasos, desde cero hasta una evidencia de nivel avanzado; no presupone experiencia previa en el tema.

Los pasos 1–10 construyen fundamentos, 11–20 desarrollan práctica y diagnóstico, y 21–30 integran el tema en un resultado más cercano al trabajo profesional. Marca cada casilla solo cuando puedas mostrar la evidencia indicada.

## Tema 18: Introducción al API Testing

**Meta:** matriz de pruebas con contrato, datos y resultados esperados

**Contexto de práctica:** verificar el contrato de tracking consumido por varios clientes

**Conocimientos que conecta:** REST, JSON y estrategia de testing

### Pasos 1–10: nivel Principiante

- [ ] **Paso 1.** Describe el problema de industria «verificar el contrato de tracking consumido por varios clientes» y quién recibe valor de resolverlo.
- [ ] **Paso 2.** Escribe el resultado experto observable: matriz de pruebas con contrato, datos y resultados esperados.
- [ ] **Paso 3.** Enumera lo que ya sabes y los prerrequisitos mínimos para estudiar introducción al api testing.
- [ ] **Paso 4.** Define un glosario propio para las piezas de REST, HTTP, status codes, JSON, JSONPath y primer flujo en Postman.
- [ ] **Paso 5.** Dibuja el modelo, flujo o sistema físico de REST, HTTP, status codes, JSON, JSONPath y primer flujo en Postman antes de memorizar términos.
- [ ] **Paso 6.** Prepara Postman y API local de práctica; registra versión, comandos y una forma segura de limpiar el laboratorio.
- [ ] **Paso 7.** Encuentra en learning.postman.com/docs/ una explicación oficial y anota qué conceptos confirma.
- [ ] **Paso 8.** Traza un caso exitoso de «verificar el contrato de tracking consumido por varios clientes» desde la entrada hasta el resultado.
- [ ] **Paso 9.** Resuelve «crear casos para éxito, validación, no encontrado y autorización» con la solución más pequeña que funcione.
- [ ] **Paso 10.** Provoca el error «validar solo el código HTTP sin comprobar la respuesta útil» en un entorno desechable y captura la evidencia.

### Pasos 11–20: nivel Intermedio

- [ ] **Paso 11.** Diagnostica el fallo anterior paso a paso; explica causa, síntoma y corrección, sin ocultar el error.
- [ ] **Paso 12.** Implementa la pieza central de REST, HTTP, status codes, JSON, JSONPath y primer flujo en Postman y sepárala de presentación/configuración cuando corresponda.
- [ ] **Paso 13.** Añade pruebas para caso normal, borde, entrada inválida y una regresión del fallo provocado.
- [ ] **Paso 14.** Compara dos enfoques para «verificar el contrato de tracking consumido por varios clientes» y registra un criterio medible para elegir.
- [ ] **Paso 15.** Especifica entradas, salidas, errores esperados y supuestos del componente de introducción al api testing.
- [ ] **Paso 16.** Revisa validación, permisos, datos sensibles, unidades o seguridad funcional pertinentes a REST, HTTP, status codes, JSON, JSONPath y primer flujo en Postman.
- [ ] **Paso 17.** Introduce un fallo propio del dominio —por ejemplo entrada inválida, inconsistencia, pérdida de conexión o error de colaboración— y define cómo recuperarte.
- [ ] **Paso 18.** Mide una propiedad adecuada al problema —tiempo, calidad, error, consultas, recursos o esfuerzo— y conserva la línea base.
- [ ] **Paso 19.** Optimiza solo una limitación demostrada y compara la medición antes/después.
- [ ] **Paso 20.** Comprueba persistencia, reinicio, reproducibilidad o restauración del resultado «matriz de pruebas con contrato, datos y resultados esperados».

### Pasos 21–30: nivel Avanzado

- [ ] **Paso 21.** Automatiza build, análisis o verificación del ejercicio para detectar regresiones al cambiarlo.
- [ ] **Paso 22.** Documenta una decisión técnica y enlaza evidencia primaria consultada en learning.postman.com/docs/.
- [ ] **Paso 23.** Pide revisión a otra persona o usa una checklist; corrige un problema concreto de claridad o robustez.
- [ ] **Paso 24.** Completa un laboratorio autónomo que produzca «matriz de pruebas con contrato, datos y resultados esperados» y guarda entrada, salida y pruebas.
- [ ] **Paso 25.** Evalúa el laboratorio contra criterios explícitos: corrección, casos límite, seguridad y evidencia.
- [ ] **Paso 26.** Conecta introducción al api testing con REST, JSON y estrategia de testing; dibuja el contrato entre ambos conocimientos.
- [ ] **Paso 27.** Diseña una parte del proyecto integrador para «verificar el contrato de tracking consumido por varios clientes» y registra dependencias y riesgos.
- [ ] **Paso 28.** Construye esa parte, ejecuta las pruebas y registra qué no cubre el entorno de laboratorio.
- [ ] **Paso 29.** Amplía hacia el nivel avanzado con una restricción real: escala, concurrencia, tolerancia a fallos o incertidumbre.
- [ ] **Paso 30.** Explica el sistema sin notas, defiende una decisión con evidencia y enseña a otra persona a reproducir «matriz de pruebas con contrato, datos y resultados esperados».

**Criterio de salida:** entrega «matriz de pruebas con contrato, datos y resultados esperados», explica «validar solo el código HTTP sin comprobar la respuesta útil» y demuestra cómo introducción al api testing se conecta con REST, JSON y estrategia de testing.
